# VERIFY-01 제품·평가 정책 독립 검토

2026-09-22 KST · 첫 인계 · 검토 대상 ADR-002 proposed, 아래 SHA256 기준.

## 판정과 소유권 ACK

**수정 후 채택 권고. 현 문구 그대로의 채택에는 반대한다.** 고객 300개·경영주 120개 총량, family 분할, 95%/90%/85% 문턱, 불변식 0건, 후보 6/6·연속 비개선 3회는 유지한다. 아래는 baseline 실행 전 정책 반례이며 실제 앱의 평가 실패 판정이 아니다. 아직 고정 baseline 결과는 없다.

VERIFY-01 revision 1, card/CORE/index/GOAL/ADR-002 및 17/21/23/24/27을 직접 읽었다. README·02·09·20·ADR-001·docs 작업 규칙과 PROGRESS의 현재 포인터/최근 DATA02 기록도 대조했다. PROGRESS 상단은 UI09A, 하단 최신 DATA02는 25e1e9d여서 상단을 현 배포 증거로 재사용하지 않았다. 이번 검토는 실제 배포를 재검증하지 않는다.

제품/평가 독립 검토자이며 **이 파일만 작성**한다. 상대 method 보고서는 읽지 않았고, 다른 agent를 호출하지 않았다. 앱·ADR·공유 문서·사용자 `.idea/`는 수정하지 않는다. 최초 환경 확인에서 읽기 전용 `git status --short`를 1회 실행한 것은 요청의 no-git 범위를 벗어난 절차 실수다. Git 변경/원격 작업은 없으며 이후 Git 명령은 실행하지 않았다. live/network/browser/build/테스트는 실행하지 않았다.

`wanna-gs-decide`의 사용자 불변식 우선·두 관점 독립 검토·사후 문턱 완화 금지에 따라 최소 수정안을 제안한다. 이 보고서는 두 검토 중 한 관점이며 조정자의 채택 또는 제품 QA/G5/G6 PASS가 아니다. D-46에 따라 UI11 Preview를 기다리게 하지 않는다.

## 채택 전 필요한 최소 수정

### P1-1. 420개 총 사례와 baseline 420호출을 분리해야 한다

근거: ADR 규칙 2/3/8은 선정 후 독립 holdout을 요구하지만 규칙 9는 baseline 420회를 기본으로 적었다. 60/20/20을 정확히 적용하면 dev 252, validation 84, holdout 84다. baseline에 420개를 모두 실행해 실패를 분석하면 protected holdout을 먼저 소비한다. 반대로 holdout을 안 돌리면 규칙 9의 420회는 사례 수와 맞지 않는다. 다턴 대화 1개는 1회 호출도 아니다.

최소 대체 문구:

> 총 고유 사례는 고객 ≥300·경영주 ≥120이며 dev/validation/holdout의 합이다. baseline은 dev+validation만 실행한다. 정확한 60/20/20일 때 336사례이고 final holdout 84사례는 best 선정 후 평가자만 실행한다. family 반올림 후 실제 사례 수·대화 turn 수·허용 재시도·반복수를 manifest에 고정해 API 호출 상한을 별도 합산한다. 420을 최초 baseline 호출 수로 고정하지 않는다. 기존 공개 smoke는 dev 증거이며 baseline/holdout을 대체하지 않는다.

holdout 원문·정답뿐 아니라 정답을 역추론할 수 있는 case별 실패 설명/trace도 튜닝 담당에게 전달하지 않는다. 공개에는 hash·집계·접근 기록만 남긴다. 실패 내용을 열어 복구했다면 해당 family는 regression으로 옮기고, 독립 새 holdout family를 선정 버전의 최종 평가에 사용한다. 계정 한도 unknown을 무제한 승인으로 해석하지 않으며 필요 예산 부족은 미실행이지 통과가 아니다.

### P1-2. 분모·채점 단위가 열려 있어 오류를 빼고 통과할 수 있다

근거: 규칙 4의 문턱이 규칙 5의 E2E/응답 정확도 중 어느 분모에 적용되는지 없다. 예컨대 60개 중 20개 transport 실패를 버리고 응답한 40개만 모두 맞으면 100%로 출시 판정할 수 있다. JSON 불량/refusal까지 ‘모델 응답 없음’으로 빼는 것도 같은 문제다. 재시도 성공을 새 사례로 세면 분모가 달라진다.

최소 추가 문구:

> 역할·split·채점 slice마다 사전에 고정한 전체 case ID를 출시 문턱의 E2E 분모로 사용한다. transport/timeout/스키마 실패는 정상 과제 성공이 아니다. 미실행 case가 있으면 해당 필수 판정은 incomplete이며 PASS를 내리지 않는다. 응답이 도착한 해석 정확도는 별도 진단 지표로 보고하고, malformed/refusal도 도착한 응답 분모에서 제거하지 않는다. 기대 거절인 사례만 올바른 거절을 성공으로 센다. quota/auth/provider 장애와 앱/모델 오답을 원인별로 분리하되 출시 증거 누락을 면제하지 않는다.

> 고유 대화 1개는 여러 turn/재시도가 있어도 1 case다. 필수 단계·최종 허용 행동·금지 행동을 함께 판정하고 일부 turn 정답으로 전체 성공을 만들지 않는다. 허용 retry 후 최종 결과, 첫 실패, 실제 호출/사용량을 함께 보존한다. 반복 실행은 반복수이지 새 고유 사례가 아니다. `ceil(문턱×n)`의 n·필수 성공 수를 결과 전에 저장한다.

프로바이더 장애는 상품 부재·점포 미취급·재고 0·공급 제한과 다르다. 정상 검색 실패에 ‘상품이 없다’고 답하거나 미식별 니즈를 저장하면 안전한 거절 성공으로 채점하지 않는다(VAL-02/04).

### P1-3. 정상·모호·미식별·정정·거절을 한 평균으로 묶지 않는다

근거: 규칙 4의 ‘모호/미식별/정정/거절 등 ≥90%’는 실패를 숨길 수 있다. 예상 거절 90개를 맞히고 정정 후 가능한 정상 검색 10개를 모두 거절해도 90%다. 명확 사례가 극소수여도 명확 95%와 전체 평균을 맞출 수 있다. 규칙 3의 7개 위험 범주만으로 정상/거절 균형이 자동 보장되지는 않는다.

최소 추가 문구:

> 각 역할·validation/holdout에는 정상적으로 과제를 완수할 수 있는 사례를 최소 절반 배정한다. 이는 두 역할의 정상 서비스가 주목적이기 때문이며, 정상 사례에도 오타·문맥·수량/조건 등의 위험 tag를 붙여 7개 범주를 충족할 수 있다. 나머지에는 모호 확인·실제 미식별·제약 밖 거절·실패 복구를 사전 배정한다. 정정 뒤 명확해지는 대화는 정상 완료도 필수다. 정상과 기대 거절/보류 성공률을 각각 보고하며 서로 상쇄하지 않는다. 90%는 모호·미식별·정정·거절의 각 적용 slice에 따로 적용한다. slice별 최소 사례 수/3개 이상의 독립 family와 분모를 baseline 전 manifest에서 고정하고 빈 필수 slice는 실패로 취급한다.

300/120 총량을 늘리거나 95/90/85를 낮추자는 제안이 아니다. 적은 분모의 엄격함을 사전에 드러내야 한다. 예: n=3에서 ceil(0.85×3)=3이므로 3/3이 필요하다. 경영주 24개 validation 전체에서 1개 차이는 4.17%p이지만 ‘명확 명령’ 분모는 그보다 작을 수 있다. 합격선은 실제 slice 분모로 계산해야 한다.

family는 ID 이름만 다른 문장 묶음이 아니라 동일 필요·의도·상품/상태 조합에서 파생한 모든 말투·오타·번역을 연결한 split 단위다. 공개 화면 예시/연구 문서의 합성 예시/기존 smoke·그 family는 dev에 둔다. 연구 taxonomy와 공개 catalog 자체의 공유는 허용하지만 공개 예시의 단어만 바꾼 문장을 holdout으로 만들지 않는다. overall case는 중복 합산하지 않고, 중첩 위험 tag의 각 slice 분모와 family별 성적을 별도 공개한다.

### P1-4. ‘후보가 들어 있음’과 올바른 SKU 확인·업무 완료는 다르다

근거: 규칙 4는 ‘올바른 후보/선택 유도’를 구체 채점 계약 없이 둘 수 있다. 모든 SKU를 후보로 보내거나 원상품 대신 유사 대체품을 내도 recall은 높다. catalog에 존재하는 SKU여도 고객이 제외한 맛/규격이면 오답이다. ‘규격 미확인’을 모델이 임의로 채우거나 조건 row 누락을 미취급으로 단정하면 허구 ID 0건만으로는 잡지 못한다. 경영주도 intent만 맞고 이번 한도를 지속 예산으로 저장하면 실패다.

최소 추가 문구:

> case oracle에 허용 SKU 집합/확인 필요/정정 후 목표·명시 필수/제외 속성·근거 없는 주장·금지 상태변화를 고정한다. 후보 k는 실행 전 계약으로 제한하고 Recall@k와 최종 올바른 선택 유도를 분리한다. 정답 SKU가 후보에 포함됐다는 사실만으로 성공하지 않는다. 대체 상품은 원상품 식별 정답으로 세지 않으며 별도 표시·새 상품/점포/수량/가격 확인·새 동의와 원래 흐름 복귀를 검사한다. 규격/조건 unknown은 unknown으로 남긴다. 경영주 core는 intent+이번만/지속 scope+전체 조건의 완전 일치와 최종 상태를 함께 판정한다.

불변식 0건은 실행뿐 아니라 유효 후보로 수락된 가짜 SKU, 동의 없는 변경, 확약 수량 오염 등을 포함한다. 모델 원시 잘못된 제안과 로컬 서비스의 차단은 둘 다 기록하되, 차단이 정상 업무 성공을 대신하지 않는다. mandatory 정상 자동발주·고객 요청→픽업 여정·권한/48시간 경계의 결정적/브라우저 인수 검사는 통계적 자연어 95% 허용 오차로 면제하지 않는다.

### P2-5. 승인 버튼만 줄이면 UX 부담 기준을 우회할 수 있다

근거: 규칙 11은 고객 텍스트 입력/점포 선택/체크를 별도로 기록만 하고, 경영주 화면 이동·완료 시간에도 문턱이 없다. 10품목을 개별 화면에서 열고 체크 10번 한 뒤 승인 1번이면 현재 문구는 통과한다. 잘 아는 정확명에 구분 질문을 항상 2회 요구해도 질문 상한만 충족한다. 이는 D-12·CORE-25·VAL-08의 업무 감소를 증명하지 않는다.

최소 추가 문구:

> 동일 seed·업무량·입력 난이도·시작/종료 상태의 실제 재현 가능한 기준 흐름과 후보를 사전 고정한다. 고객은 입력 시작→요청 저장 완료까지 전체 필수 조작/질문/화면 이동·P50/P95, 경영주는 같은 10품목 묶음의 전체 필수 조작/화면 이동/승인·P50/P95를 센다. 텍스트 편집·점포 선택·동의 조작을 총 부담에서 제외하지 않는다. 동등 작업에서 전체 필수 조작·화면 이동·불필요 질문 증가 0, 완료 시간 P95 악화 ≤20%를 개선 후보의 사전 허용폭으로 둔다. 도구/네트워크 대기·실패·표본/반복수는 함께 기록하며 성공 실행만 골라 시간을 비교하지 않는다.

> 기존 제출/확인 ≤4회·명확한 정규명에서 불필요 구분 질문 0회·실제로 모호한 사례의 추가 확인 ≤2회, 정상 묶음 승인 1회·승인된 자동발주 건별 승인 0회·중복 발주/알림 0건을 유지한다. 필요한 동의나 예외 확인을 없애 숫자를 맞추지 않는다. 정상 자동발주 성공과 예외 노출/복귀를 별도 필수 흐름으로 검사한다. 고객 상세 열람은 승인 횟수가 아니지만 화면 이동/시간에는 포함한다.

시간 20%는 규칙 7의 지연 회귀 허용폭과 일관된 **사전 제안**이며 관측 성능에 맞춘 수치가 아니다. 최초 baseline 자체는 비교할 이전 앱 결과가 없으므로, 실제 재현 가능한 고정 control과 절대 흐름 기준으로 측정한다. 존재하지 않는 과거 성능을 만들거나 ‘개선 없음’을 ‘검증 불필요’로 해석하지 않는다. 브라우저 agent 측정은 인간 사용성 연구가 아니다.

### P2-6. 현재 범위와 채택/개선 판정의 작은 빈칸을 닫는다

- ADR context/scaffold 설명·depends_on은 현재 VERIFY-01/DATA02와 D-46로 갱신하고 AC-32·CORE-26을 명시한다. **‘본 ADR/PLAN-READY는 중간 화면 Preview의 게시 선행조건이 아니며 최종 goal 품질 판정에 적용’**을 추가한다. 262/524 배포 기록은 전체 자료 출처/좌표 검증 완료와 구분한다. RS-20260921만 고정하지 말고 채택한 현재 research/catalog/scenario/eval manifest를 연결한다.
- 규칙 7의 개선은 주 채점 지표·분모·paired 차이·‘경계선’ 조건·추가 비교의 판정 결합을 사전 고정한다. 같은 사례를 다시 돌려 더 좋은 실행만 고르면 안 된다. **‘추가 비교 시 baseline/candidate 모두 동일 횟수 실행, 모든 반복을 함께 보고, 필수 기준은 각 유효 실행에서 충족; 낮은 표본의 1~2건 개선은 유한 표본 개선이며 통계적 우월성 아님’**을 추가한다. 한도 6/6·연속 3회 비개선은 유지한다.
- 모델 비교가 허용되므로 규칙 8의 ‘동일 model/config’는 **‘변경 대상으로 사전 선언한 요인 외 모든 조건·split·채점 규칙 동일’**로 고친다. 모델만 바꾸는 유효 후보를 금지하거나 prompt/config 실험을 문구상 불가능하게 만들지 않는다. 모델 변경으로 후보/호출 한도를 초기화하지 않는다.
- 지연 P95 30초는 ‘개선 목표’인지 ‘출시 최소’인지 규칙 4/6에 명시한다. 정책 선택은 baseline 전 수행하고 provider 장애를 해당 성능 PASS로 바꾸지 않는다. 실제 retry/timeout 구현 적합성은 별도 method/state 관점이며 이 보고서에서 실행 확인했다고 하지 않는다.

## 목적 보존·다음 행동

유지할 정상 결과는 고객의 정확한 상품 요청→동의→점포 수요→경영주 적은 개입의 보수적 발주→모의 결제/입고→48시간 픽업이다. 모든 요청 거절·대체 상품 강제·상시 건별 승인·질문 반복으로 안전 점수를 만들지 않는다. 미식별 니즈를 보존하되 시스템 장애와 추천 관심을 실제 수요에 섞지 않는다.

조정자가 두 독립 보고의 반례를 대조해 ADR/실행 manifest에 최소 수정하고 보완 ACK를 받으면 채택 가능하다. 기준 결과를 보기 전 split·slice·분모·허용 행동·UX workload·호출 상한을 고정한다. 이 검토를 기다리며 UI11을 멈추거나 새로운 전체 사전점검을 시작할 필요는 없다. 현재 앱 성능·실제 모델·보호 holdout·CI·G5/G6는 검증 미실행이다.
