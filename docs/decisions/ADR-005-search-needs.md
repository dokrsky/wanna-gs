# ADR-005: 제한된 추가 질문과 니즈 기록

- 상태: adopted, 구현·실행 검증 전
- 권한 근거: user-delegated, D-14/25/37/44~46. CORE-02~04/11/21/23/25와 O-11, AC-01~04/29/31.
- 날짜/제안자: 2026-09-21 조정자. base `b4a2854`, UI-07 후보. `policy_key=search.needs.v1`.
- effective_scope: `codex/ui-preview-20260921` 후속 구현. depends_on: ADR-001/003. supersedes/conflicts_with: 없음. 사용자 직접 확정·평가 PASS가 아니다.

## 목적과 최소안

고객이 설명을 보완해 상품을 찾을 수 있고, 찾지 못한 니즈를 중복 구매 수요로 만들지 않고 남겨야 한다. 검색·추정·대체 후보·확인한 구매를 구별한다. 최대2회 추가 질문을 채택하고, 새 프레임워크 없이 현재 검색 UI/서버와 SQLite의 부가 기록을 확장한다.

## 대화와 출력

1. 한 검색 대화는 최초 입력과 추가 질문 최대2회다. 질문2회는 의무가 아닌 상한이며 명확한 후보는 질문/니즈 등록 없이 기존 구매 확인폼으로 진행한다. 성공한 모델 결과 `clarify`를 고객에게 표시할 때 유효 응답 ID별 최초 표시에서 한 번만 질문 횟수를 증가시킨다. API 실패·취소·낡은 응답은 횟수/니즈를 증가시키지 않는다. 2개 질문에 답한 뒤 세 번째 질문 대신 원래 제약 검사를 통과한 후보의 명시 선택 또는 미식별·기록/새 검색 경로를 제공한다. 유효 후보가 있으면 모두 거절하지 않는다.
2. 입력 수정은 현 대화의 답변 초안을 바꾼다. 명시적인 ‘새 상품 찾기’는 대화/질문 횟수/후보 초안을 새로 시작하며 이미 저장한 요청·니즈를 삭제하지 않는다. 모드 전환·reset·역할/대화 전환 뒤 늦은 결과는 해당 대화를 변경하지 않는다. 일반 새로고침은 저장된 니즈/실행 기록은 복원하되 미저장 입력·진행 중 모델 호출을 자동 재호출하지 않는다.
3. 각 입력300자 상한을 유지하며 서버에는 최초 입력을 별도로 보존해 현재 답변·최대2개의 이전 질문/답변 쌍과 함께 전달한다. 최초 제외/필수 조건은 고객이 명시적으로 변경하기 전까지 유지한다. 현재 서버 카탈로그 ID만 후보 최대3개로 허용한다. 서버/클라이언트가 동일 계약을 검사한다. 모델·키·서버 카탈로그를 클라이언트가 지정하지 못한다. 필요한 검색 body 상한은 UTF-8 8KiB, 출력/시간 상한은 기존 provider 계약을 유지한다.
4. 후보별 정확 후보/확인 필요/대체를 구분한다. 모델이 붙인 분류/단서는 추정이지 고객의 확정 동의가 아니다. 대체는 ‘찾으신 것과 다른 상품’으로 표시하고 카탈로그의 확인 가능한 속성으로 공통점/차이를 설명한다. 명시적 제외/필수 조건을 위반한 후보나 속성 근거 없는 보장 문구를 허용하지 않는다. 좋은 대체 근거가 없으면 후보 없이 기록 경로를 제공한다.
5. 후보 노출/선택/거절은 검색 이력이며 원래 요청·SKU·점포·동의·순번을 변경하지 않는다. 선택한 후보로 구매하려면 기존 확인 폼에서 수량·한 점포·가격·새 동의를 받는다. 기존 활성 동일SKU/점포 요청 중복은 ADR-003으로 거절하고 자동 취소·전환하지 않는다.

## 저장과 조회

6. 검색이 정상 완료되면 식별 결과와 단서·후보·모드·모델·사용량·실행 시각을 검색 이력으로 보존한다. 저장 완료 전 저장됐다고 표시하지 않으며, 자동 검색 이력은 고객의 명시 등록 전 경영주에게 공유하지 않는다. 원 대화 ID는 연결 키, 행동별 저장 키는 재시도 동안 고정하며 같은 키·다른 본문은 거절한다. 고객이 명시적으로 한 점포를 골라 ‘못 찾은 니즈 남기기’를 실행하면 한 대화의 미식별 기록을 한 건·한 점포로 확정한다. 이후 점포 선택/재시도로 자동 이동·복제하지 않는다. 2회 질문 전에 고객이 더 설명하지 않기로 선택한 경우도 `clarification_stopped`로 구분해 남길 수 있다. 로컬 저장 실패는 검색 실패와 구분하고 유효 결과·동일 저장 명령을 유지해 저장만 재시도한다. 모델 재호출·질문 재계수·미식별 확정을 하지 않는다.
7. 니즈 원문/대화, 정제 단서, 단서의 원문 근거·불확실성, 식별 상태/사유·관측 시각·후보 IDs를 보존한다. 카탈로그 미식별, 점포 조건 미확인, 모의 요청 불가, 고객이 후보를 거절한 경우를 구별한다. 조건 누락을 실제 미취급·품절·생산 종료로 바꾸지 않는다. 시스템/모델 오류는 실행 오류 기록으로만 남기고 미식별 니즈로 확정하지 않는다. 동일 실행 시도의 성공/오류 결과는 배타적이고 실제 새 모델 호출은 별도 실행으로 기록한다.
8. 원문/대화와 모델 실행 상세는 고객 본인만 조회한다. 경영주는 자기 점포에 명시 전달된 니즈의 합성 고객 식별자·상품 관련 허용 속성으로 투영한 단서·정해진 사유 코드·후보·시각만 조회한다. 원문에 실제 포함된 개인정보도 원문 인용·자유문장 사유·중첩 단서에서 제외하고 안전하게 분리하지 못한 단서는 제외한다. 원문·타점포/타세션을 기본 노출하지 않는다. 요약은 모델 추정/고객 확인을 구분하며 확인하지 않은 개인정보를 만들어 넣지 않는다. 경영주에게 니즈별 승인·회신 의무를 만들지 않는다. 본부 화면/분석 API는 추가하지 않는다.
9. 추천 노출/선택/거절·후속 요청 연결은 별도 사건으로 기록하고 행동별 원 사건 ID로 중복을 막는다. 하나의 대화 ID 때문에 서로 다른 노출/선택 사건이 사라져서는 안 된다. 이 부가 기록 명령은 거래 정산·자동발주·결제·동의 만료 처리까지 부수 실행하지 않는다. 유효 구매 요청이 별도로 생성된 경우만 수요에 합산한다.
10. 현재 schema1의 알려진 sourceHash에서만 비파괴적 SQL 추가 마이그레이션으로 기록 테이블을 만든다. 기존 모든 행·관계와 요청/발주/결제/예약/예산/receipt fingerprint/result/시각/순번/세대/보관 이력을 보존하고 bootstrap·시각 재기산을 하지 않는다. 새 snapshot 영구 저장 완료 후 공개하며 실패하면 이전 bytes와 재시도 경로를 유지한다. 정상 v1의 저장 실패는 손상/reset 오류가 아닌 재시도 오류로 처리한다. 알 수 없는/손상된 사본을 자동 reset하지 않는다.
