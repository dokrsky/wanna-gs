## 문제와 대안

계획 문서만 존재하는 단계에서 배포 가능한 정적 데모가 추가됐다. 현재 배포/health 성공은 실제 SQLite·두 역할·모델 품질 성공을 증명하지 않는다. 초기 scaffold를 최종 제품으로 판정하지 않도록 실행 단계와 기준을 고정한다. 모든 제품 검사를 초기 CI에 요구하면 순환 의존이 생기므로 단계별 필수 집합을 확장한다. 모델 응답을 본 뒤 표본/합격선을 줄이는 대안은 기각한다.

## 제안 정책

1. runtime은 설치된 Node 24.12.0과 Vercel 24.x를 사용하고 `.nvmrc`/engines/CI를 맞춘다. lockfile 한 작성자, 결정적 `npm ci`. 현재 Next.js 기반을 재사용하되 실제 취약점은 원인/영향을 검토 후 호환 패치한다.
2. 고객 300개·경영주 120개 이상의 서로 다른 합성 발화/대화 사례를 유지한다. 연구→시나리오→case를 연결하고 60/20/20 목표로 **family** 단위 분할한다. 크기 반올림 때문에 비율이 조금 달라도 각 핵심 범주가 validation/holdout에 최소 3개 family를 갖도록 평가자가 확인한다. 같은 의도/상품/상태의 번역·오타·말투 변형은 동일 split이다.
3. 최소 각 역할 7개 위험 범주를 21번에서 도출한다. 검색 200+ SKU의 정확 ID/정규명 결정적 검사는 별도다. 300개를 200개 정규명 반복으로 채우지 않는다. 공개 예시·그 패러프레이즈는 dev만 사용한다. holdout 원문/정답은 독립 nl-evaluator만 접근하는 Git 무시 private 산출물에 보관하고 앱/정적자산/프롬프트에 넣지 않는다. 공개 저장소에는 hash·집계·절차만 기록한다.
4. 출시 최소: 거래 불변식 위반 0건; 존재하지 않는 SKU를 유효 후보로 수락 0건; 명확 고객 요청의 올바른 후보/선택 유도 및 명확 경영주 핵심 intent/scope/조건 완전 일치 각각 ≥95%; 모호/미식별/정정/거절 등 허용 행동 ≥90%; 위험 범주별 ≥85%. 평가자는 분모와 ceil(문턱×분모)를 사전 고정한다. validation과 final holdout 모두에 적용한다. 전체 평균으로 범주 실패를 덮지 않는다. 모델 원시 오류와 서버/로컬 서비스의 최종 거절을 각각 집계한다.
5. transport 실패까지 포함한 end-to-end 성공 분모와 모델 응답이 있는 해석 정확도 분모를 모두 보고한다. API 오류는 상품 미등록/품절로 채점하지 않는다. 정상 사례를 모두 보류하면 성공 기준을 충족하지 못한다. 입력당 모델 요청 최대 1회, 네트워크/429 일시 오류에만 최대 1회 재시도; quota 부족은 중단한다. 내부 모델의 생각/원문 오류/키는 로그에 넣지 않는다.
6. 지연 목표는 각 역할 live validation P95 ≤30초, 정상 요청 timeout 45초다. 초기 실행 baseline은 낮은 동시성(최대 2)으로 측정한다. 목표를 실패 후 완화하지 않고 provider 장애와 앱 지연을 분리 기록한다.
7. 개선 목표: 같은 validation에서 오류 ≥2건 감소 또는 정확도 +2%p, 필수 오류 0건 유지, 각 범주 기준 유지, 새 정상 경로 실패 0건, P95 지연이 기준선 대비 20% 넘게 악화되지 않음. 표본 1~2건 차이를 통계적 우월성이라고 주장하지 않는다. 경계선 후보는 같은 사례로 한 번 추가 비교하고 모든 실행을 보존한다.
8. 최대 후보 고객 6/경영주 6/전체 12, 역할별 연속 비개선 3회면 그 역할 추가 최적화를 종료한다. mandatory 결함은 별도 복구이며 한도 리셋 수단으로 이름을 바꾸지 않는다. baseline→빠른 dev 선별→validation→선정 best의 독립 holdout 순서다. 비교를 위해 baseline/candidate를 동일 model/config/split에서 실행한다.
9. API 실행 계획은 단계마다 먼저 고정한다. 최초 preflight 실호출 상한 4회(기존 연결 검사 1회 재사용), 최초 두 역할 통합 smoke 상한 24회. 전체 eval은 기본 baseline 420회 + 후보 선별/validation의 남은 상한 + final holdout 재검증/두 역할 G6 여유를 평가 실행 계약에서 계산하고 계정 확인 가능한 한도와 대조한다. 잔액은 현재 unknown이며 무제한 호출 승인이 아니다. response usage를 집계하고 quota 시 선택 실험부터 멈추되 필수 검사를 fixture로 대체하지 않는다. 후보별로 전 420개를 반복하지 않는다.
10. 데이터는 200+ 독립 SKU·20~30 최근 관심/신상품 후보의 근거 상태·8~12 실제 점포/좌표·합성 고객 약20명·점포별 합성 경영주 1명을 유지한다. availability는 결정적 20~35% 희소 분포, 정상 상품은 복수 점포/희소 후보는 1~3점포, 거래 값은 simulated. 최신 조사 RS-20260921의 출처를 독립 검토 후 자료 계약에 채택한다. 좌표를 임의 합성해 verified로 표시하지 않는다.
11. 고객 390px/360px, 경영주 1280px에서 실제 브라우저 QA. 정규명 정상 요청에서 후보 확인부터 요청 완료까지 필수 제출/확인 동작 ≤4회(텍스트 입력/점포 선택/체크 조작은 별도로 기록), 추가 구분 질문 ≤2회. 경영주 10개 품목의 동일 묶음은 승인 1회, 각 고객 상세 열람은 승인 횟수에 포함되지 않으며 독립 접근 가능해야 한다. 승인된 자동발주 정상 품목에는 건별 승인 0회. 반복 조회로 발주/알림 수 증가 0건. 기능 개선 전후 같은 시나리오의 조작/시간을 보고하고 필수 확인·동의를 삭제해 수치를 맞추지 않는다.
12. gate runner는 phase별 실제 테스트 결과·계약 fingerprint·별도 구현자/검토자·정상/실패 목적 보존 증거를 읽는다. 누락/0개/skip/stale/자기검증/자식 FAIL/live에 fixture를 거절한다. CI aggregate `gate`는 항상 결과를 내고 보호 규칙은 기존 요구를 유지하며 허용된 범위에서 PR+check 강제를 연결한다. 로컬 결과의 무서명 한계를 명시한다.

## 검증과 효력 확대

두 독립 검토는 기준의 분모/범주 편향·holdout 분리·비용 추정·UX 조작 계산·bootstrap 순환을 검토한다. 연구/실제 Preview가 준비돼야 PLAN-READY를 판정한다. 채택 후 21/23번 관련 기준과 평가 manifest·실행 예산·작업 계약을 연결하고 결과를 보고 변경하지 않는다. 통합 branch 검증과 PR 이전에는 전역 verified 정책이 아니다.
