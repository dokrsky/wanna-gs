## 결과와 제한

공식 공공데이터포털의 지정 다운로드 한 번에서 받은 바이트를 실제 파싱해, 서울 CSV의 지정된 업소번호 **6개 모두**를 찾았다. 각 행은 39개 필드를 가진 완전한 CRLF 종료 레코드다. 상호·도로명주소가 기존 점포와 대응하고, 좌표 문자열은 [직전 보고서](store-origin-followup.md)의 Purpleo 값과 6/6 일치한다. 소수 여섯 자리로 반올림하면 현재 `data/stores.json`의 좌표와도 모두 일치한다. 좌표 변경을 제안하거나 적용하지 않았다.

그러나 **352,699,739바이트 ZIP 전체 다운로드는 실패했다.** 사용자 지정 120초 제한에서 curl이 종료 코드 28로 멈췄고, 받은 길이는 **252,608,512바이트**다. 서울 CSV의 압축 데이터도 끝부분이 잘려 있다. 확보한 압축 스트림의 앞부분에서 6개 대상 행을 모두 읽은 것이며, ZIP 중앙 디렉터리·서울 CSV 전체 CRC·전체 파일 SHA-256까지 검증한 결과가 아니다. 이 구분을 없애고 `full_archive_verified`나 `full_csv_verified`로 승격하면 안 된다.

## 실제 다운로드·부분 추출 실행 증거

1. `df -k /private/tmp`: 가용 **27,797,680 KiB** 확인. `mktemp -d /private/tmp/wanna-gs-store-primary.XXXXXX`로 새 디렉터리 생성.
2. curl 8.7.1에서 `--fail --silent --show-error --max-time 120 --connect-timeout 15 --max-filesize 360000000 --get`을 사용했다. 재시도·Range·이어받기·병렬 전송은 없다. 실행 중 세션을 짧게 확인했으며 중단 가능한 전송이었다.
3. **02:10:47 KST** 완료 관측: HTTP 200, `application/octet-stream; charset=UTF-8`, 수신 **252,608,512 / 352,699,739바이트**, 소요 **120.007736초**, curl exit **28**(timeout). 제한 이후 재요청하지 않았다.
4. 중앙 디렉터리가 없으므로 완전한 ZIP으로 열었다고 주장하지 않는다. Python stdlib `struct`로 로컬 헤더의 파일명/길이를 읽고, 다른 멤버는 압축 크기만큼 seek했다. 출력한 멤버 목록은 **서울 CSV 하나**다. 다른 CSV의 압축 해제/행 파싱은 하지 않았다.
5. 서울 멤버만 stdlib `zlib.decompressobj(-15)`로 스트리밍 해제하고, `csv.reader(..., strict=True)`로 UTF-8 39열을 파싱했다. 대상 ID가 아닌 행은 검색 과정에서 메모리를 통과한 뒤 버렸고 출력/별도 저장하지 않았다. 디스크에 풀어 쓴 CSV는 없다. 사용자 허용대로 받은 원본 ZIP 부분 파일만 저장소 밖에 남겼다.
6. 파싱 가능한 prefix의 완전한 레코드 **498,824개**에서 대상 **6개/고유 ID 6개**, 대상 중복 0개, 누락 0개를 관측했다. 이 집계는 전체 서울 CSV의 행 수/ID 유일성 검증이 아니다. 마지막 줄의 불완전한 38바이트는 레코드로 읽지 않았다.
7. 별도 자체 재대조에서 압축 입력 청크를 64KiB→1MiB로 바꾸어 다시 해제하고, 첫 실행이 보고한 여섯 바이트 구간만 수집했다. 각 원행의 길이·SHA-256·CRLF·1레코드/39필드가 일치했다. CSV prefix의 길이·SHA도 동일했다. 이는 추출 자체 검사이며 독립 에이전트 검토/앱 테스트가 아니다.

| 서울 CSV 전체 | 301,889,640(로컬 헤더 선언) | **미확보**, 전체 CRC도 미검증 |

선택 CSV 해시는 원본 706바이트 header와 원행 6개의 원래 UTF-8/따옴표/CRLF를 그대로 이어 붙여 계산했다. 재직렬화하지 않았고 별도 CSV 파일로 저장하지 않았다. **선택 CSV 해시를 공식 전체 CSV 해시로 부르지 않는다.**

### 원행 해시와 재현 위치

행 SHA-256은 39열 원본 레코드 바이트 전체이며 마지막 CRLF를 포함한다. 레코드 번호는 header 제외 1-based, 물리 줄 번호는 header 포함 1-based, byte offset은 **압축 해제된 서울 CSV 시작 기준 0-based**다. 모두 한 물리 줄의 완전한 레코드다.

## 연구→후속 적용과 남은 범위

`RC-ST-ORIGIN-01`의 공식 행 미열람 0/6 상태는 이번 **공식 배포 스트림에서 완전한 대상 행 6/6 관측**으로 보완됐다. `SP-SEMAS-META/ATTACH → RC-ST-ORIGIN-01 → DEMO-ST-01/02/03/04/05/08 → SC-ST-ORIGIN-01`로 추적한다. 점포 ID·좌표·요청 FK·snapshot 불변 확인은 이 연구에 연결할 공개 합성 회귀 시나리오이며 실제 앱/DB에서 실행하지 않았다. 새 eval 질의/정답이나 holdout은 만들지 않았다.

main이 provenance에 반영할 때는 원문 파일 이름/배포 버전·공식 URL·업소번호·선택 행 SHA·관측 필드를 분리하고 **`archiveComplete:false`, `csvComplete:false`, `csvCrcVerified:false`, `selectedRowsObserved:6`**에 해당하는 제한을 함께 보존해야 한다. 이는 제안이며 데이터 필드를 실제 변경한 것이 아니다. 현재의 `originalDistributionRowVerified`가 완전한 원배포 무결성 또는 Purpleo의 역사적 취득 판을 의미한다면 이 증거만으로 무조건 true로 바꾸지 않는다. 별도 필드 범위 판단·독립 검토는 데이터 소유자의 후속이다.

남은 것: 전체 ZIP/서울 CSV SHA·CRC, 전체 서울 내 ID 유일성, Purpleo의 과거 취득 판/변환 이력, CRS/좌표 생성·갱신/측량 정확도, 현재 영업·출입구·재고, 독립 data QA. 기존 ST06/ST07 조사·이용조건은 이번 범위 밖이다. 시간 제한으로 잘린 다운로드를 이유로 데이터 수정이나 다른 아카이브 수집을 계속하지 않는다. 현재 결과는 검증된 부분 인계이며 전체 DATA/EVAL/G1~G6 완료가 아니다.

목적 보존: stores/provenance 바이트를 유지했고 거래·동의·픽업·역할 관계를 수정하지 않았다. 실제 수행한 검사는 공개 출처/바이트 추출/자체 재대조다. 앱 테스트·브라우저·실제 모델 호출은 0회다. 공유 PROGRESS에 옮길 결과·증거·블로커·다음 행동은 이 문서를 main에 인계한다.

마감 확인: **2026-09-22 02:14:29 KST**, 시작 관측 후 **6분 13초**에 결과·문서·보존 경로를 점검했다. 임시 디렉터리에는 위 부분 ZIP 한 개만 있으며 stores/provenance 해시와 revision2 context 해시가 유지된다. 문서의 6개 ID/좌표/행 지문과 부분·전체 해시 구분, 줄 끝 공백을 확인했다. 이 마감 기록을 추가한 뒤 소유권을 반환하며 추가 다운로드/조사는 수행하지 않는다.
